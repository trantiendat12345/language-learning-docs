# Schema Change Log

> Vì dự án **chưa dùng Flyway** (`spring.jpa.hibernate.ddl-auto=update` — rủi ro đã ghi ở `docs/PROJECT_OVERVIEW.md` mục 10.3), không có migration script nào tự động ghi lại lịch sử thay đổi schema. File này là nơi **ghi tay thủ công** mỗi khi entity thay đổi, để: (1) không mất dấu vết vì sao 1 cột tồn tại, (2) có sẵn tư liệu viết migration script thật khi chuyển sang Flyway ở Giai đoạn 10, (3) tester dùng để biết khi nào cần đối chiếu lại `docs/testing/07_DATA_DICTIONARY.md`.

## Cách dùng

Mỗi khi thêm/sửa/xoá entity (thêm bảng, thêm/xoá/đổi kiểu cột, thêm constraint), thêm 1 dòng vào bảng dưới đây **trong cùng commit** với thay đổi code. Sau đó cập nhật `docs/testing/07_DATA_DICTIONARY.md` nếu field đó ảnh hưởng tới hợp đồng dữ liệu mà tester cần biết.

**Bug phát hiện khi code Grammar (2026-07-29):** `GrammarServiceImpl.deleteGrammar()` soft-delete Grammar cha rồi mới gọi `grammarExampleRepository.findAllByGrammarId(id)` để cascade soft-delete example — nhưng derived query `findAllByGrammarId` (dựa trên field association `grammar`) sinh ra JOIN sang bảng `grammar`, và Hibernate áp `@SQLRestriction("is_deleted = false")` của `Grammar` vào chính JOIN đó; vì Grammar cha đã `is_deleted=1` ngay trước đó trong cùng transaction, JOIN không khớp và query trả về rỗng — example con vẫn còn `is_deleted=0` dù Grammar cha đã bị xoá. Phát hiện qua test thật (tạo Grammar + 2 example, xoá Grammar, kiểm DB trực tiếp thấy example vẫn `is_deleted=0`). Sửa bằng cách thêm field shadow đọc thẳng cột FK (`grammarId`, `insertable=false, updatable=false`) trên `GrammarExample` để Spring Data query thẳng cột `grammar_id`, không JOIN — áp dụng phòng ngừa tương tự cho `LessonVocabulary.lessonId`/`vocabularyId` dù chưa quan sát được lỗi thật ở đó (rủi ro cấu trúc giống hệt: `Lesson`/`Vocabulary` đều có `@SQLRestriction`). Đã verify lại bằng curl + kiểm DB: xoá Grammar mới tạo → example cascade `is_deleted=1` đúng.

## Lưu ý khi chuyển sang Flyway (Giai đoạn 10)

Khi tới lúc thêm Flyway: dùng chính log này làm checklist để viết lại toàn bộ lịch sử thành các file `V1__init.sql`, `V2__add_frequency_rank.sql`... theo đúng thứ tự thời gian đã ghi — đảm bảo baseline migration khớp với schema thực tế đang chạy (`ddl-auto=update` đã tạo ra), không viết migration "tưởng tượng" khác với DB thật đang có.
